## Bug Fixed This Session: exec_hi = -1 → 0

### Root Cause
`WidenExecOperation()` in `comgr-hotswap-transpiler-helpers.cpp` was setting `exec_hi = -1` when mirroring `s_mov_b32 exec_lo, -1`. In wave32→wave64 with a 32-thread workgroup, exec_hi should be 0 (only lanes 0-31 are valid). Setting exec_hi=-1 activated lanes 32-63 which have undefined work-item IDs (v58), causing them to:
1. Compute wrong LDS addresses (v12, v13, v14)
2. Write garbage data to random LDS locations during global→LDS copy
3. Corrupt valid data written by lanes 0-31

### Fix
Changed line 196 in `comgr-hotswap-transpiler-helpers.cpp`:
```cpp
// BEFORE:
hi_src = "-1";   // WRONG: activates invalid lanes 32-63

// AFTER:
hi_src = "0";    // CORRECT: only lanes 0-31 active
```

The WMMA→MFMA handler already explicitly sets `s_mov_b64 exec, -1` when it needs all 64 lanes for the MFMA instruction and restores the original exec afterward. This fix doesn't affect the MFMA path.

### Result
Before fix: mixed zero pattern (rows {2,8,10} zero, row 0 partially zero, some columns zero)
After fix: clean zero pattern (rows {0,2,8,10} entirely zero, all columns uniform)

## Remaining Bug: Zero Rows {0, 2, 8, 10}

### Pattern Analysis
- Zero rows: m ∈ {0, 2, 8, 10} = rows where bit0=0 AND bit2=0
- Affected w32 lanes: {0, 2, 8, 10, 16, 18, 24, 26}
- Affected MFMA lanes (via scatter-back mapping): {0,2,8,10,16,18,24,26,32,34,40,42,48,50,56,58}

### What Is Verified Working
1. **MFMA hardware**: Standalone test confirms v_mfma_f32_16x16x16_f16 with all-1.0 inputs → 16.0 everywhere (256/256)
2. **LDS address coverage**: All ds_read_u16 addresses for every lane land within ds_write_b128 written regions (verified by Python script)
3. **Gather mapping**: Correct — all MFMA lanes map to valid w32 source lanes 0-31
4. **Scatter-back**: Correct for lanes 0-31 (exec_hi=0 prevents garbage from lanes 32-63)
5. **Epilogue/activation**: GELU gradient correctly produces 16.0 when MFMA output is non-zero
6. **Store path**: Only lanes 0-31 store (exec_hi=0 at store time)
7. **D buffer SRD**: Correct (s[16:19] with proper base/size)

### LDS Read Pattern for Zero-Row Lanes
Zero-row lanes read from byte position 0 (element 0) or byte position 4 (element 2) within each write block:
- Lane 0 (row 0): reads element 0 from even threads {0,2,4,...,14}
- Lane 2 (row 2): reads element 2 from even threads {0,2,4,...,14}
- Lane 8 (row 8): reads element 0 from odd threads {1,3,5,...,15}
- Lane 10 (row 10): reads element 2 from odd threads {1,3,5,...,15}

Non-zero lanes read element 1 or element 3, e.g.:
- Lane 1 (row 1): reads element 1 from even threads → NON-ZERO (16.0)

### Hypothesis: Global Load Returns Zeros for Elements 0 and 2
The buffer_load_dwordx4 loads 16 bytes (8 f16 values = 4 dwords v[42:45]) per thread.
- Element 0 = bytes [0:1] of v42 (low 16 bits of v42)
- Element 1 = bytes [2:3] of v42 (high 16 bits of v42)
- Element 2 = bytes [0:1] of v43 (low 16 bits of v43)
- Element 3 = bytes [2:3] of v43 (high 16 bits of v43)

If the global load returns `0x3C000000` instead of `0x3C003C00` for some dwords (i.e., low 16 bits = 0, high 16 bits = 0x3C00), elements 0 and 2 would be zero while elements 1 and 3 are non-zero.

This could happen if the buffer load offset (v8) is wrong, causing the load to read from unaligned or wrong addresses where the low f16 of each dword pair is 0.

### Next Steps to Investigate
1. **Trace v8 (global load offset)** — Decode the .long v_mul_lo_u32 instructions at lines 815-816, 820-821, 825-826, 830-831 to understand how each thread's global address is computed. Check if the address formula is correct for the transpiled wave64 kernel.

2. **Instrument the kernel** — Create a debug version that stores the raw global load data (v[42:45]) to a separate buffer before the ds_write, to verify what was actually loaded from global memory.

3. **Check if v8 depends on v58** — If v8 uses `v58 >> 5` (which is 0 for all 32 threads in a single-wave workgroup), the address might be wrong. The original wave32 kernel computed addresses based on 32 threads; in wave64, the thread ID mapping may differ.

4. **Alternative: Try a subagent for v12/v13 trace** — Background agent analysis found that threads 0-31 and 32-63 have DIFFERENT v12 values (A-matrix LDS addresses) but SAME v13 values (B-matrix). With exec_hi=0, only threads 0-31 write, so the +32 offset for threads 32-63 is irrelevant. But the v12 computation uses `(v66 >> 5) & 1` as a "virtual wave ID" — in the original wave32 kernel this was 0 for threads 0-31 and 1 for threads 32-63 (two waves). In wave64 with exec_hi=0, there's only one set of threads 0-31, and `(v58 >> 5) & 1` = 0 for all of them. This might mean the second half of the A matrix never gets written to LDS.
